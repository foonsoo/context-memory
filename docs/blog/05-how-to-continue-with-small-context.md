# 긴 문서를 읽지 않고도 작업을 이어갈 수 있을까

지난 글에서는 흩어진 기억을 현재 결정, 이유, 제약, 대안, 결과와 변경 이력으로
묶어 Decision Wiki를 만드는 과정을 이야기했다. 사람이 한 주제의 판단을 오래
읽고 검토하기에는 이런 문서가 유용했다.

하지만 새 AI 세션에서 “방금 하던 일을 계속해줘”라고 요청할 때마다 여러 Wiki
페이지 전체를 읽는 것은 지나치다. 지금 필요한 것은 프로젝트의 모든 역사가
아니라, 어디서 무엇을 이어가야 하는지 알려주는 작은 인계 카드에 가깝다.

이번 글을 시작한 과정이 실제 사례였다. 처음 세션이 열린 곳은 이름만 같은 빈
저장소였다. 그곳에는 앞선 블로그 원고도 최신 코드도 없었다. 그러나 이전 사건에
남은 정식 저장소 경로와 검토된 기억을 따라 실제 원고를 찾고 다음 작업을 이어갈
수 있었다.

이 경험은 다음 질문으로 이어졌다.

> 세션도, 정확한 폴더도, 이전에 사용한 표현도 모르는 상태에서 지금 필요한
> 맥락만 작게 복구할 수 있을까?

## Wiki와 작업 인계는 필요한 크기가 다르다

Decision Wiki는 한 결정의 이유와 역사를 이해하기 위한 문서다. 반면 작업을
재개하려는 AI에는 다음 정보면 충분한 경우가 많다.

- 어떤 정식 프로젝트를 말하는지
- 실제 저장소는 어디에 있는지
- 현재 유효한 결정과 사실은 무엇인지
- 마지막으로 끝낸 일과 다음 작업은 무엇인지
- 확인해야 할 파일은 무엇인지
- 더 깊이 검증할 때 따라갈 원본 사건은 무엇인지

그래서 최근에는 **Context Recall**이라는 별도의 읽기 경로를 추가했다. 세션을
먼저 시작하거나 과거 세션 번호를 알 필요 없이 현재 폴더와 자연어 요청만으로
작은 맥락 묶음을 만든다.

Wiki가 책상 위에 펼쳐 놓는 의사결정 문서라면, Context Recall은 다음 담당자에게
건네는 인계 카드라고 할 수 있다. 둘은 같은 근거를 사용하지만 목적과 분량이
다르다.

## 현재 폴더는 경계가 아니라 단서다

보통 개발 도구는 현재 열린 폴더를 프로젝트의 경계로 사용한다. 하지만 임시
폴더에서 AI를 시작하거나, 같은 프로젝트를 다른 경로에 다시 내려받거나, 이름만
같은 빈 저장소를 열 수도 있다.

Context Recall은 현재 폴더를 중요한 단서로 보되 유일한 검색 범위로 사용하지
않는다. 현재 위치에서 답을 찾지 못하면 공유 기억과 최근 사건에서 관련
프로젝트를 찾는다.

이전 사건에 정식 저장소 경로가 명시되어 있다면 이름만 같은 빈 폴더보다 그
경로를 우선한다. 반대로 두 프로젝트의 근거가 비슷하면 어느 쪽도 선택하지 않고
모호하다고 답한다. 최근에 작업했다는 이유만으로 관련 없는 프로젝트의 기억을
가져오지도 않는다.

핵심은 더 적극적으로 찾는 것보다, 충분히 확실할 때만 하나의 프로젝트를 고르는
것이다.

## 기본 결과는 작은 토큰 예산 안에 넣는다

프로젝트를 찾았다고 모든 기억을 전달하면 긴 대화를 다시 만드는 것과 다르지
않다. Context Recall은 기본적으로 약 350개의 추정 토큰 안에서 결과를 구성한다.

긴 기억은 질문과 관련된 문장으로 줄이고, 원본 전문과 상세한 검색 진단은 처음
응답에서 제외한다. 필요할 때 사건 ID를 따라 원본을 다시 확인할 수 있다.

정확한 토크나이저도 핵심 의존성으로 추가하지 않았다. 모델마다 토큰을 세는
방식이 다르고 별도의 모델 데이터가 필요하기 때문이다. 대신 모델과 무관한
보수적인 추정치를 사용하고, 실제 비용이나 넘침 문제가 측정될 때 다시 검토한다.

목표는 모든 역사를 가장 짧게 요약하는 것이 아니다. 다음 행동을 안전하게
시작할 만큼의 정보만 먼저 전달하는 것이다.

## 파일도 찾되 저장소 전체를 읽지는 않는다

초기 Context Recall은 기억에 명시된 파일만 보여줬다. 하지만 실제 작업에서는
필요한 결정은 기억에 있고 정확한 파일명은 저장소에만 있는 경우가 있었다.

이 실패를 확인한 뒤, 프로젝트가 먼저 안전하게 선택된 경우에만 해당 정식
저장소에서 관련 파일을 제한적으로 찾도록 바꿨다.

- 숨김 파일과 심볼릭 링크는 따라가지 않는다.
- 살펴볼 디렉터리 항목, 텍스트 파일 수, 전체 읽기 크기에 상한을 둔다.
- 관련 경로는 최대 세 개만 반환한다.
- 파일 내용 전체가 아니라 경로만 작은 맥락 예산에 포함한다.
- 파일 검색 결과를 프로젝트 선택의 근거로 사용하지 않는다.

순서가 중요하다. 먼저 기억과 사건으로 프로젝트를 선택하고, 그 뒤에 선택된
저장소 안에서만 파일을 찾는다. 파일 탐색 결과가 잘못된 프로젝트 선택을 스스로
강화하지 않도록 경계를 둔 것이다.

저장소 탐색은 파일을 읽는 수뿐 아니라 디렉터리를 살펴보는 과정에도 상한을
둔다. 제한을 적용하기 전에 전체 파일 목록부터 만드는 방식은 큰 저장소에서
사실상 제한이 아니기 때문이다.

## 한국어 요청과 영어 기록 사이의 작은 간격

실제 평가에서는 필요한 작업 기록을 찾았는데도 표현 차이 때문에 다음 단계를
놓치는 사례가 있었다. 사용자는 한국어로 “같은 인계 내용을 확인해”라고 했지만
기록에는 `same handoff`라고 적혀 있는 식이었다.

모든 기억을 번역 모델에 보내는 방식은 사용하지 않았다. 대신 평가에서 확인된
일부 작업 표현에 한해 제한된 영어 대응어를 덧붙인다. 최대 개수를 정하고 기존
토큰 예산 안에서만 적용하며, 어떤 표현이 보완됐는지도 확인할 수 있다.

거대한 의미 변환 계층을 추가하기보다 실제 실패가 있었던 작은 간격부터
측정하며 메운 선택이다.

## 검토된 기억이 없으면 최근 사건으로 돌아간다

방금 끝난 작업은 아직 장기간 사용할 기억으로 정리되지 않았을 수 있다. 이때
검토된 기억만 검색하면 가장 필요한 최신 인계를 놓치게 된다.

Context Recall은 세션을 새로 만들지 않고 최근의 원본 사건을 제한적으로 확인할
수 있다. 먼저 현재 폴더와 연결된 사건을 보고, 그것으로 프로젝트를 식별할 수
없다면 공유 데이터베이스의 작은 사건 범위에서 질문과 직접 관련된 프로젝트가
정확히 하나인지 확인한다. 동점이거나 근거가 약하면 선택하지 않는다.

원본 사건에서 가져온 항목은 검토된 기억인 척하지 않는다. 기억 ID 대신 사건
ID를 남겨 출처의 성격을 구분한다. 이는 3편에서 다룬 ‘정리된 기억과 최신 작업
사이의 간격’을 세션 없이 이어가기 위한 형태로 발전시킨 것이다.

## 두 읽기 방식은 경쟁하지 않는다

Context Recall이 생겼다고 Decision Wiki가 불필요해진 것은 아니다. 둘은 같은
근거를 서로 다른 시간 크기로 읽는다.

| 필요 | 적합한 읽기 방식 |
| --- | --- |
| 지금 어느 파일에서 작업을 이어갈지 알고 싶다 | Context Recall |
| 현재 결정과 다음 단계를 빠르게 복구하고 싶다 | Context Recall |
| 결정의 이유와 대안, 결과를 검토하고 싶다 | Decision Wiki |
| 결정이 바뀐 과정을 개정 이력으로 보고 싶다 | Decision Wiki |
| 요약이 맞는지 확인하고 싶다 | 인용된 기억과 원본 사건 |

Wiki는 사람이 반복해서 읽고 검토할 안정된 관점을 제공한다. Context Recall은
AI가 세션 경계를 넘어 행동을 재개할 수 있도록 작은 현재 맥락을 제공한다. 둘 다
새로운 사실을 만들어내지 않고 같은 출처를 따라간다.

처음에는 잘 만든 Wiki 문서가 모든 기억 문제의 답이 될 것처럼 보였다. 실제로
사용해보니 ‘이해를 위한 문서’와 ‘재개를 위한 맥락’은 분량도, 검색 방법도,
필요한 최신성도 달랐다.

## 숫자는 가능성을 보여줄 뿐 보장은 아니다

변경된 로직은 재현 가능한 평가를 거쳤다. 한국어와 영어로 표현된 24개의 고정된
작업 재개 질문에서는 파일, 결정, 다음 단계와 원본 출처를 모두 찾았다. 해당
평가에서 다른 프로젝트 선택과 오래된 기억 유출은 관찰되지 않았고, 반환 크기의
중앙값은 376 추정 토큰, 최대값은 512였다.

별도로 실제 사용에서 나온 두 질문을 사후 재생한 평가에서도 기대한 맥락과
출처를 복구하고 금지된 정보는 섞지 않았다. 하지만 이는 이미 발생한 질문을
다시 실행한 결과다. 아직 보지 못한 모든 실제 요청에서 같은 성능을 보장하지
않는다.

그래서 합성 평가와 실제 사용의 사후 평가는 구분해 기록한다. 새로운 실제
요청은 구현을 조정하기 전에 기대 결과와 출처를 먼저 고정해야 더 강한 검증이
된다. 테스트에 잘 맞는 시스템과 낯선 다음 요청에서도 도움이 되는 시스템은
같지 않을 수 있기 때문이다.

## 필요한 만큼만 기억을 펼친다

Context Recall의 목적은 기억을 더 많이 보여주는 것이 아니다.

- 현재 폴더 밖에서도 관련 프로젝트를 찾는다.
- 하나의 프로젝트를 확실히 선택할 수 없으면 멈춘다.
- 현재 결정과 다음 작업을 작은 예산 안에 담는다.
- 선택된 저장소 안에서만 관련 파일을 제한적으로 찾는다.
- 검토된 기억이 없으면 최근 사건을 보되 둘을 구분한다.
- 더 깊은 확인이 필요하면 원본 사건으로 돌아간다.

이번 글도 이 흐름으로 이어졌다. 빈 폴더에서 시작했지만 최근 사건이 정식
저장소를 알려줬고, 검토된 기억이 시리즈의 목적과 문체를 복구했으며, 저장소에서
앞선 원고와 최신 로직을 확인할 수 있었다.

이제 다음 질문이 남는다.

> 서로 다른 AI 도구가 이 작은 맥락을 같은 방식으로 이어받을 수 있을까?

다음 편에서는 특정 AI 제품의 대화 기록에 묶이지 않고 여러 AI가 같은 근거와
현재 맥락을 공유하도록 만든 방법을 이야기한다.
